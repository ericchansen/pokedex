## How to use this

1. **Read `functional-spec.md` first** — it defines the four views, design principles, and all functional requirements (FR-*).
2. **Read `schema.md` for data contracts** — it documents every JSON file the app must consume. Implement to the contract, not to the fixture data.
3. **Load `data/` at runtime as seed data.** Don't couple your implementation to flat JSON files; the spec (§4) says storage format is an implementation choice.
4. **Completeness is derived, never stored.** No `status`, `tier`, or `completeness` fields exist on builds or teams. Compute them at runtime by inspecting the data.

## Key relationships

- **Builds** are the atomic unit — species, nature, EVs, moves, item, ability all live on the build
- **Teams** are 6 FK references to builds (`{ slot, build_id }`) — no data duplication
- **Inventory** is a 200-box × 30-slot grid that mirrors real Pokémon HOME storage
- **Presets** are organizational templates (Living Dex layouts) overlaid on the inventory

## What's NOT in here

- Implementation choices (framework, bundler, backend) — agent decides
- UI design / visual mockups — the spec describes behavior, not pixels
- Test plans — agent should write tests appropriate to their implementation
- Existing code (`serve.py`, `site/js/`, etc.) — current incomplete implementation, start fresh
